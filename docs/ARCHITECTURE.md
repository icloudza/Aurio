# 架构设计

本文说明 Aurio 的整体结构、传输协议，以及缓冲、漂移补偿、麦克风和回声消除的实现方式。

## 1. 总览

Aurio 由三部分组成：

| 组件 | 语言 | 职责 |
|---|---|---|
| 核心库 `aurio-core` | Rust | 协议编解码、抖动缓冲、漂移补偿、重采样、麦克风上行打包、回声分析。两端共用，不依赖操作系统 |
| Mac 端 `mac/AurioMac` | Swift + Rust（通过 `aurio-ffi` 的 C 接口） | CoreAudio 输出 / 输入、语音处理（回声消除）、Bonjour 广播、菜单栏界面 |
| Windows 端 `aurio-win` + `apps/win-tauri` | Rust | WASAPI 回环采集、麦克风写入虚拟线、默认设备设置、驱动管理、Bonjour 发现、Tauri 图形界面 |

数据流：

```
播放    Windows 系统声音 → WASAPI 回环采集 → 打包 → UDP → 接收线程 → 环形缓冲 → 渲染回调（漂移补偿 + 重采样）→ 输出设备
麦克风  输入设备 → 输入回调 → 环形缓冲 → 上行线程（下混、重采样、打包）→ UDP → Windows 接收 → 抖动缓冲 → CABLE Input
控制    Windows 每 0.5 s 发心跳（可带「需要麦克风」）→ Mac 原样回应（附带本端状态）→ Windows 计算往返时间
```

两个方向共用同一对 UDP socket，默认端口 47800。Mac 只把数据发给最近一个向它发包的地址，所以不需要额外的握手。

### 实时线程的约束

音频设备回调（Mac 的 AUHAL 渲染 / 输入回调，Windows 的 WASAPI 事件线程）中不分配内存、不加锁、不做系统调用。线程之间只通过无锁单生产者单消费者环形缓冲（`rtrb`）和原子变量交换数据。Windows 的音频线程注册到 MMCSS「Pro Audio」任务，网络线程提升到最高优先级，避免被调度推迟。

## 2. 传输协议

每个 UDP 包由 24 字节固定包头和 PCM 负载组成，所有字段都是小端序。

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | magic | 固定为 `ND` |
| 2 | 1 | version | 当前为 1 |
| 3 | 1 | type | 1 = 音频，2 = 心跳，3 = 控制（保留） |
| 4 | 1 | stream_id | 0 = 播放方向（Windows → Mac），1 = 麦克风方向（Mac → Windows） |
| 5 | 1 | flags | 见下表 |
| 6 | 2 | reserved | 0 |
| 8 | 4 | seq | 包序号 |
| 12 | 8 | sample_index | 本包第一帧在流中的位置。起始值按当前时间生成，发送端重启后序号一定变大 |
| 20 | 2 | frames | 本包帧数 |
| 22 | 2 | format_id | 采样格式编号 |

**标志位**

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | MUTED | 发送端静音 |
| 1 | FORMAT_CHANGED | 格式发生变化 |
| 2 | DISCONTINUITY | 发送端采集出现断档（例如 WASAPI 报告 discontinuity） |
| 3 | MIC_REQUEST | 心跳：Windows 上有应用正在录音，请求 Mac 打开麦克风 |
| 4 | HEARTBEAT_ACK | 心跳回应：收到心跳后原样返回（seq 不变），用于检测连通和测量往返时间 |
| 5 | AEC_ACTIVE | 心跳回应：Mac 正在做回声消除 |

**采样格式**

| 编号 | 格式 | 用途 |
|---|---|---|
| 1 | 48 kHz / 24 bit / 立体声 | 播放方向 |
| 2 | 48 kHz / 24 bit / 单声道 | 麦克风方向 |
| 3–5 | 16 bit 立体声 / 单声道、44.1 kHz 立体声 | 保留 |

默认每包 120 帧（2.5 ms）。播放方向每包 744 字节，每秒 400 包，约 2.4 Mbps；麦克风方向约 1.2 Mbps。包大小远低于以太网 MTU（负载上限 1448 字节），不会分片。

## 3. 播放方向

### 3.1 Windows 采集

- 使用 WASAPI 共享模式回环采集默认播放设备（或用户指定的设备），事件驱动。共享模式的引擎周期固定为 10 ms，所以数据每 10 ms 一批。
- **静音补包**：系统没有播放声音时，回环采集不交出任何数据。Aurio 从开始采集的那一刻起，按真实时间补发静音包（始终落后真实时间 10 ms，与正常采集节奏一致），保证接收端的数据流不中断，第一次出声时也不需要重新缓冲。
- 采集断档时在下一个包上标记 DISCONTINUITY。

### 3.2 Mac 接收

接收线程解析包头，按 `sample_index` 把数据写到环形缓冲的正确位置：

- 迟到或重复的包（落后 1 秒以内）直接丢弃，局域网中极少出现。
- 小于 0.5 秒的空洞补零（计为丢帧）。
- 更大的跳变视为发送端重启，重新对齐（resync）。

### 3.3 抖动缓冲与漂移补偿

Windows 和 Mac 的声卡时钟各自独立，频率差异通常在几十到几百 ppm。不处理的话，缓冲会持续变多（延迟累积）或变少（欠载爆音）。Aurio 用一个 PI 控制器调节重采样比例，把缓冲稳定在目标值。

**控制最低水位，而不是平均水位。** 发送端每 10 ms 送来一批数据，缓冲量本身是锯齿波。100 ms 窗口内的最低点才反映离欠载还有多远，而且不受批大小影响。

| 参数 | 默认值 | 说明 |
|---|---|---|
| 控制窗口 | 100 ms | 统计最低水位的窗口 |
| 比例 / 积分增益 | 0.2 /s、0.01 /s² | 偏差被拉回的速度 |
| 修正上限 | ±500 ppm | 重采样比例的最大调整量 |
| 目标水位 | 1 ms + 1.5 × 抖动峰值 | 上限 40 ms |
| 抖动峰值衰减 | 半衰期 600 s | 网络变好后，目标水位缓慢下降 |
| 目标下降速度 | 最多 0.02 ms/s | 上升不限速 |
| 欠载补偿 | 每次欠载目标 +1 ms | 出现欠载后立即多留余量 |
| 多余数据丢弃 | 最低水位超过目标 15 ms 时 | 例如启动时缓冲期攒下的数据，直接丢弃，不慢慢消化 |

抖动峰值取自两个来源：「包到达的最大间隔 − 采集周期」，以及窗口最低水位向下偏离的幅度。控制器不会周期性地「往下试探」，那样会主动制造爆音。

开播和欠载恢复时做 1 ms 淡入，避免爆音。

### 3.4 重采样

自研的可变比例重采样器，使用 Kaiser 窗 sinc 分数插值：

- 默认单侧 32 个抽头（共 64 个），固定延迟约 0.67 ms。
- 每次调用都可以改变比例，所以漂移补偿只需要调整步长。
- 同时负责采样率转换：输出设备不是 48 kHz 时，直接转换到设备采样率。
- 系数表在构造时一次算好，处理过程中不分配内存。

### 3.5 Mac 输出

通过 AUHAL 按 UID 锁定输出设备（默认自动选择 Studio Display），不跟随系统默认输出变化；设备拔出后会等它重新出现，自动恢复。IO 缓冲 128 帧。渲染回调直接调用 Rust 的 `aurio_rx_render`。

## 4. 麦克风方向

### 4.1 按需开启

麦克风模式有三种：自动、常开、关闭。在「自动」模式下：

1. Windows 控制线程检测「CABLE Output」上是否有处于活动状态的录音会话，也就是有没有应用正在录音。
2. 有的话，在心跳中带上 MIC_REQUEST。
3. Mac 收到请求后打开麦克风；超过 3 秒没有收到请求就关闭麦克风。

这样平时不占用麦克风，macOS 菜单栏也不会一直显示麦克风使用指示。

### 4.2 Mac 上行

输入回调把采样写入环形缓冲；上行线程负责下混为单声道、重采样到 48 kHz、打包，然后发给最近一个对端。

### 4.3 Windows 写入虚拟线

Windows 端的渲染线程以 CABLE Input 的设备时钟为准拉取数据，并复用核心库的抖动缓冲和漂移补偿（与 Mac 播放端是同一套代码），然后写入 CABLE Input。应用从 CABLE Output 录音。WASAPI 队列余量默认 5 ms，可以通过 `--mic-queue-ms` 调整。

选择 VB-Cable 而不是自研驱动：Windows 内核驱动需要 EV 证书和微软签名，自研成本过高。

## 5. 回声消除

打开回声消除后，Mac 在需要麦克风时不再使用普通的 AUHAL 输入 / 输出，而是改用 **VoiceProcessingIO** 音频单元，同时负责：

- **播放**：Windows 传来的声音经它输出，它因此知道扬声器正在播放什么，以此作为回声参照。
- **采集**：输出经过回声消除、降噪和自动增益处理的麦克风信号。

实现要点：

- 输出和输入都绑定到 Studio Display，使用它的完整麦克风阵列，系统音量压低（ducking）设为最小。
- 同一时间只有一个音频单元向接收缓冲取数据：切换时先停掉普通输出，再启动语音处理单元。
- 启动失败时自动退回普通输出和普通麦克风，并在面板上提示。
- 麦克风关闭后恢复普通输出（原始音质）。
- 运行状态通过心跳回应的 AEC_ACTIVE 标志告诉 Windows，界面上会显示「回声消除」标签。

核心库的 `echo` 模块提供回声分析：把参照信号和麦克风录音降到 8 kHz 后做归一化互相关，得出回声延迟、强度和能量占比。Windows 的「录音测试」使用的就是这个模块。

## 6. 发现与连接状态

- **发现**：Mac 用 Bonjour 广播 `_aurio._udp` 服务（端口 47800，TXT 记录 `v=1`），Windows 用 mDNS 浏览，同时支持手动填写地址。
- **Mac 端状态**：2 秒内收到过音频包，显示「正在播放」；只收到心跳，显示「已连接 · 没有声音」；都没有，显示「连接已断开」。
- **Windows 端状态**：3 秒内收到过心跳回应，显示「已连接」，否则显示「Mac 没有响应」。

## 7. Windows 系统集成

- **默认设备**：通过 `IPolicyConfig` 设置默认播放 / 录音设备，供「一键修复」和安装驱动后使用。
- **驱动管理**：从 VB-Audio 官网下载官方驱动包，解压后用 Authenticode 校验签名者。然后以管理员身份重新启动自身（`Aurio.exe --driver-helper install|uninstall|status`）执行静默安装。卸载时用 `pnputil` 清理设备、音频端点和驱动包。整个过程只弹出一次 UAC 确认框。
- **托盘与生命周期**：关闭窗口时按设置缩到托盘或退出；单实例（再次启动时激活已有窗口）；开机自启参数 `--tray`。托盘图标根据注册表 `SystemUsesLightTheme`（任务栏主题，不是应用主题）切换黑白两套。

## 8. 延迟构成

有线局域网下的实测和估算：

| 环节 | 延迟 | 说明 |
|---|---|---|
| Windows 回环采集 | 0–10 ms，平均约 5 ms | 共享模式引擎周期 10 ms，数据成批交出 |
| 网络 | < 0.5 ms | 有线局域网 |
| Mac 抖动缓冲 | 约 5–8 ms | 自适应的安全余量 |
| 重采样 | 0.67 ms | 固定 |
| Mac IO 缓冲与安全偏移 | 约 3 ms | 128 帧 IO 缓冲加设备安全偏移 |
| Studio Display 内部处理 | 22 ms | 驱动报告的输出延迟（1056 帧），软件无法压缩 |
| **合计** | **约 35–45 ms** | 实测：游戏中稳定在 35–43 ms |

进一步降低延迟的空间主要在 Windows 采集周期上：Windows 10 起的 `IAudioClient3` 低延迟共享模式可以把周期降到约 3 ms，但需要声卡驱动支持，预计能节省 3–5 ms。

## 9. 测试

- 核心库有单元测试：`cargo test --release -p aurio-core`。
- `aurio-sim` 离线仿真可以模拟时钟偏差、采集周期、抖动和丢包，快速验证长时间运行的稳定性。例如时钟偏差 +80 ppm、抖动 2 ms 的条件下，仿真 24 小时零欠载。
- `aurio-send` 可以在没有 Windows 的情况下向 Mac 发送测试信号。
